# 개발 원칙

## 작업 단위

- 작업은 독립적으로 검증 가능한 작은 단위로 나눈다.
- 하나의 작업에는 명확한 목적, 범위, 제외 범위와 완료 조건이 있어야 한다.
- 개별 작업은 `templates/FEATURE.md` 또는 `templates/BUG.md`를 복사해 `tasks/TASK-XXX.md`로 만든다.
- 범위가 달라지면 임의로 확장하지 않고 작업 명세를 먼저 갱신한다.

## 변경 전

- 관련 코드, 설정, 데이터 모델과 테스트를 확인한다.
- 작업 트리의 기존 변경사항을 확인하고 사용자 변경을 보존한다.
- 변경할 파일, 영향 범위, 데이터 변경 여부, 검증 방법을 정한다.
- 새 의존성은 기존 도구로 해결할 수 없는지 먼저 검토한다.

## 구현

- 프로젝트의 기존 구조, 명명법, 포매팅과 오류 처리 방식을 따른다.
- 입력은 클라이언트뿐 아니라 신뢰 경계인 서버에서도 검증한다.
- 실패를 무시하는 빈 예외 처리나 임시 우회 코드를 두지 않는다.
- 중복 요청, 재시도, 동시 수정이 데이터 중복이나 유실을 일으키지 않게 고려한다.
- 운영 설정과 개발 설정을 분리하고 비밀정보는 환경변수 또는 전용 저장소로 관리한다.
- 주석은 코드가 하는 일보다 선택 이유와 중요한 제약을 설명한다.

## 의존성과 데이터 변경

- 의존성 추가 시 목적, 대안, 라이선스, 보안 및 유지보수 영향을 기록한다.
- 잠금 파일을 함께 갱신하고 불필요한 전체 버전 변경은 피한다.
- 데이터베이스 변경은 이전 데이터와의 호환성, 마이그레이션, 실패 시 복구를 포함한다.
- 삭제나 비가역 변경은 정확한 대상과 백업을 확인한 후 수행한다.

## 문서화와 결정 기록

- 실행, 테스트, 필수 환경변수와 운영 절차가 바뀌면 관련 문서를 함께 갱신한다.
- 되돌리기 어려운 기술 선택이나 제품 범위 변경은 `docs/DECISIONS.md`에 기록한다.
- 완료 보고는 사실, 추측, 미검증 사항을 구분한다.
