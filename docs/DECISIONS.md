### 2026-08-14 — 첫 제품 범위와 핵심 사용자 확정

- 상태: 승인
- 배경: 육아 정보, 커뮤니티, 강좌와 커머스를 포괄하는 장기 비전에서 첫 개발 범위를 정할 필요가 있다.
- 결정: 첫 제품은 만 2~7세 아이의 부모 및 주 양육자를 위한 모바일 중심 반응형 웹으로 시작하고, 상황별 감정·행동 대응 가이드 탐색을 핵심 흐름으로 삼는다. 커뮤니티, 강좌, 커머스, 계정과 개인화 저장은 제외한다.
- 대안: 처음부터 육아 통합 플랫폼을 구축하거나 커뮤니티를 첫 기능으로 시작하는 방안을 검토했다.
- 이유: 가장 중요한 사용자 문제를 작은 범위에서 검증하고, 콘텐츠 신뢰성과 사용 편의성을 먼저 확보하기 위해서다.
- 영향: 초기 정보 구조, 콘텐츠 모델, 화면과 테스트는 빠른 상황 탐색 및 짧고 실천 가능한 안내를 우선한다.
- 검증: 대표 상황을 이용한 모바일 사용자 흐름 테스트로 가이드 발견 가능성, 이해도와 핵심 행동 확인 여부를 평가한다. 정량 기준은 출시 전 별도 작업에서 확정한다.
- 되돌리기: 사용자 검증 결과에 따라 연령대와 핵심 상황 범위를 `docs/PRODUCT.md`에서 재정의하고 후속 작업 명세를 조정한다.

### 2026-08-14 — 응급상황 안내의 초기 안전 경계

- 상태: 승인
- 배경: 응급상황에서 빠른 도움을 주는 것이 장기 목표지만 부정확한 판단이나 안내는 실제 피해와 치료 지연을 유발할 수 있다.
- 결정: 첫 버전은 의료 진단, 개인별 치료 지시와 독자적으로 생성한 응급 처치 안내를 제공하지 않는다. 위험 신호가 있는 경우 검증된 공공기관 및 전문가 도움으로 연결하는 안전 안내만 허용한다.
- 대안: 생성형 안내를 포함한 실시간 응급 대응 기능을 첫 버전에 포함하는 방안을 검토했다.
- 이유: 전문가 검토, 지역별 정보 관리와 임상적 안전 검증 체계가 아직 마련되지 않았기 때문이다.
- 영향: 응급 콘텐츠는 일반 육아 콘텐츠와 분리하며 공개 전에 출처 및 전문가 검토가 필수다.
- 검증: 안전 문구, 연결 정보와 위험 상황의 동작을 관련 전문가가 검토하고 사용자 흐름 테스트에서 오해 가능성을 확인한다.
- 되돌리기: 별도의 안전성·법률 검토와 운영 체계를 갖춘 뒤 작업 명세와 승인 기록을 추가하여 범위를 확대할 수 있다.

### 2026-08-14 — 모듈형 모놀리스와 분리된 근거 수집 작업

- 상태: 승인
- 배경: 사용자 웹, 근거 수집, 전문가 검토와 향후 AI 답변을 지원하면서 초기 운영 복잡도를 제한해야 한다.
- 결정: TypeScript 및 Next.js 기반 모듈형 모놀리스와 PostgreSQL을 기본으로 하고, 외부 자료 수집은 독립 실행 가능한 worker로 분리한다. 라이선스가 허용된 원문만 오브젝트 스토리지에 보관한다.
- 대안: 처음부터 마이크로서비스, 별도 검색 엔진, 전용 벡터 데이터베이스와 메시지 브로커를 도입하는 방안을 검토했다.
- 이유: 핵심 도메인과 실제 부하가 검증되지 않은 단계에서 데이터 정합성, 개발 속도와 운영 단순성을 우선하기 위해서다.
- 영향: 코드는 사용자 웹, 도메인, 데이터베이스, 근거 처리와 수집 작업의 모듈 경계를 갖는다. 확장은 측정된 병목과 독립 배포 요구를 근거로 한다.
- 검증: 핵심 사용자 흐름, 마이그레이션, 공개 데이터 권한과 수집 작업 실패 격리를 통합 테스트하고 실제 부하에서 병목을 측정한다.
- 되돌리기: 모듈 인터페이스를 유지하며 측정된 병목 모듈만 독립 서비스로 추출할 수 있다.

### 2026-08-14 — 근거와 사용자용 가이드의 분리

- 상태: 승인
- 배경: 논문, 서적, 지침과 커뮤니티를 대량 수집하는 것만으로는 정확성, 저작권과 사용자 안전을 보장할 수 없다.
- 결정: Source, Evidence Claim, Evidence Assessment, Guide, Review와 Publication을 분리하고 사람의 승인을 거친 특정 가이드 버전만 공개한다. 커뮤니티 자료는 사용자 문제 발견에만 사용하며 행동 지침의 근거로 취급하지 않는다.
- 대안: 수집한 원문을 하나의 검색 DB에 넣고 실시간 생성 모델이 직접 답하도록 하는 방안을 검토했다.
- 이유: 출처에서 최종 행동 안내까지 추적하고, 철회·정정·라이선스와 해석 오류에 대응하기 위해서다.
- 영향: 근거 수집 자동화는 공개 권한을 갖지 않으며 콘텐츠 상태, 버전, 검토자와 재검토 기한을 저장해야 한다.
- 검증: 공개 가이드의 모든 핵심 문장이 승인된 근거 또는 명시된 전문가 합의와 연결되는지 자동 검사 및 표본 검토한다.
- 되돌리기: 데이터 계층은 유지하되 평가 방식과 승인 단계를 버전으로 개정할 수 있다.

### 2026-08-14 — AI 미사용 우선의 답변 라우팅

- 상태: 승인
- 배경: 자유 생성형 답변은 비용뿐 아니라 근거 밖의 주장과 안전상 오류를 만들 수 있다.
- 결정: 선택형 요청은 AI 없이 승인 가이드를 제공하고, 자유 질문은 필요한 경우에만 짧은 분류와 승인 가이드 재구성에 AI를 사용한다. 위험 가능성, 근거 없음, 정보 부족과 출력 검증 실패 시 생성 답변을 제한한다.
- 대안: 모든 사용자 질문에 하나의 대형 모델과 긴 검색 문맥을 사용하는 방안을 검토했다.
- 이유: 답변 일관성과 추적 가능성을 높이면서 토큰, 지연과 비용을 줄이기 위해서다.
- 영향: 경로별 품질 평가, 구조화 출력, 캐시 무효화, 토큰 관찰과 안전한 실패가 필수다.
- 검증: 동일 대표 평가셋에서 분류 정확도, 근거 밖 주장, 안전 누락, 지연, 토큰과 비용을 측정하며 품질 기준을 통과한 경우에만 더 작은 모델이나 문맥을 적용한다.
- 되돌리기: 경로별 설정을 통해 특정 상황의 모델 사용을 늘리거나 완전히 비활성화할 수 있다.

### 2026-08-14 — 제어면과 제공면의 분리

- 상태: 승인
- 배경: 공개 사용자 요청, 검토 전 원문과 전문가 승인 작업이 같은 실행·권한 경계에 있으면 침해 및 장애 범위가 커지고 공개 조회가 편집 모델에 결합된다.
- 결정: 모노레포와 PostgreSQL 기반은 유지하되 공개 `web`, 비공개 `studio`, 비동기 `pipeline`을 별도 배포·자격증명 경계로 둔다. 사용자 서비스는 불변 publication snapshot에서 만든 읽기 모델만 사용한다.
- 대안: 하나의 Next.js 앱과 하나의 데이터베이스 역할로 공개 및 운영자 기능을 모두 제공하는 방안을 검토했다.
- 이유: 마이크로서비스의 운영 부담 없이 최소 권한, 장애 격리, 빠른 공개 조회와 안전한 롤백을 확보하기 위해서다.
- 영향: 앱별 자격증명, public read model, snapshot 생성과 배포별 검증이 필요하다.
- 검증: web 역할의 비공개 데이터 접근 거부, studio 장애 중 공개 조회, 이전 publication 롤백과 read model 재생성을 통합 테스트한다.
- 되돌리기: 개발 환경에서는 한 프로세스로 실행할 수 있지만 모듈·권한 경계와 별도 entrypoint는 유지한다.

### 2026-08-14 — 불변 publication snapshot과 DB outbox

- 상태: 승인
- 배경: 여러 정규화 테이블을 사용자 요청마다 조합하면 검토 시점과 노출 내용이 어긋날 수 있고, 공개 데이터·검색·캐시 갱신 중 일부만 성공할 수 있다.
- 결정: 승인된 가이드 버전을 불변 snapshot으로 만들고 publication ID로 본문, 검색과 인용을 결합한다. 공개 요청과 outbox event는 같은 PostgreSQL transaction에 기록하고 worker는 멱등하게 read model을 갱신한다.
- 대안: 현재 편집 테이블을 직접 조회하고 애플리케이션 코드에서 순차적으로 캐시와 검색을 갱신하는 방안을 검토했다.
- 이유: 공개 내용의 재현성, 원자적 작업 인계, 안전한 재시도와 즉시 롤백을 확보하기 위해서다.
- 영향: snapshot schema version, content hash, outbox lease, idempotency key와 dead-letter 상태가 필요하다.
- 검증: 중복 이벤트, worker 중단, 부분 실패, 순서 역전과 이전 publication 재활성화를 자동 테스트한다.
- 되돌리기: read model과 검색을 snapshot에서 재생성하며, outbox 처리기를 중지해 후속 공개를 일시 중단할 수 있다.

### 2026-08-14 — AI Gateway를 외부 모델 호출의 단일 경계로 지정

- 상태: 승인
- 배경: 각 앱과 worker가 모델 제공자를 직접 호출하면 개인정보 최소화, 토큰 예산, 안전 검사와 관찰 정책이 서로 달라질 수 있다.
- 결정: 제공자 SDK 사용을 `packages/ai-gateway`로 제한하고 작업별 configuration, 구조화 I/O, timeout, 비용 기록과 validator handoff를 중앙화한다. Gateway 결과는 직접 공개할 수 없다.
- 대안: 기능별 코드가 각자 모델과 프롬프트를 선택하는 방안을 검토했다.
- 이유: 비용과 공급자 변경을 통제하고 모든 AI 경로에 동일한 안전 경계를 적용하기 위해서다.
- 영향: provider adapter, configuration ID, prompt registry, 평가 및 fallback 계약이 필요하다.
- 검증: 직접 SDK import 금지 검사, 입력 최소화, timeout, 잘못된 출력, 제공자 장애와 configuration rollback을 테스트한다.
- 되돌리기: Gateway 내부 adapter를 교체하거나 모든 생성 경로를 비활성화하고 경로 0만 제공할 수 있다.
